# ContextGrabber: Embeddable Context Provider

## Preface

There is a serious call for questioning the veracity of information shared online. Considering the unprecedented amount of misinformation spread online, which is especially harmful for political efforts, and with shifts in community notes/fact-checking availability, the lack of transparency, trust, and validity of online discussion is at an all time low. While there very much is a requirement for the validation of information *posted* online, but this tool is aimed at solving the *sharing* aspect of distribution.

## Description

When a user writes to any website they can include a ContextLink that is understood by the ContextGrabber. This link points to a file/text/section of text from wherever (so long as it supports the context grabber). When someone wants to quote this text, they use the ContextGrabber via an embeddable tool - such as in X.com posts.
Ideally, the use of this tool would establish a ground source of truth for quotes, and also cause anyone who is not quoting via the ContextGrabber to be viewed as questionable in thier approach to presenting information as truth, and cause quotes that aren't shown using the ContextGrabber as questionable in thier validity.

## Usage

This tool would read the text selected and find the relevant context that the user has decided is related to this (or any part of) this quote and appends it to the resulting view, so that it looks (by default) like:

-------------------------------------
"Quote ... end of quote"
Context: "Context ... end of context"
-------------------------------------

This is useful because often there are things that people want to ensure are not taken out of context or ensure that necessary relevant information is supplied alongside whatever it is they are saying.

The ContextLink can be of a number of formats, such as a whole page, a section of a page, a literal string, etc. Each of these options also allows the user to specify whether it is presented as a link to that text or pasted out into the Context block of the view. There will be limits on the amount of text that can be displayed as context (and even as quote) with a "quote quote quote ... (link to quote)" and "context context context ... (link to context)" as truncated versions should they exceed that limit.

They can also decide where the context is placed:
Option 1: a ContextLink inside of the text where they want it, i.e. "text text text [ContextLink] text text"
which would be displayed as "text text text [Context contents] text text"
Option 2: ContextLinks at any other point in their document that has a ContextRef that can be placed elsewhere in the text, i.e. "text text text [1] text text" ... "[1](ContextLink)"
Either of these options then determine where the text is placed relative to the quote should that be possible, depending on the section of the text that is quoted, otherwise it will have to fallback to the default. An example of a failing placement would be if they have placed a ContextLink (or refContextRef) inline with instructions <TODO: need to work this one out> to add the context for the text around it, but the quoter only quotes some of that text but not the part that includes the ContextLink or ContextRef.

This allows the author to have their quote be before, during, or after the quoted text when displayed by ContextGrabber's embedded view.

# key gaps & how to fix them

## 1) platform reality (x, fb, etc.)

* your doc imagines an “embeddable tool—such as in x.com posts.” in practice, you **don’t control** how platforms render external links. you get an Open Graph/Twitter Card preview at best; no arbitrary JS. consider:

  * **phase 1:** a hosted share URL that renders a clean “quote + context” card. rely on link previews (OG tags) to tease content; clickthrough shows the full interactive.
  * **phase 2:** **browser extension** + **publisher JS widget** (wordpress/ghost/substack plugins) that add a “quote with context” button. end-run platforms.
  * **phase 3 (moonshot):** official integrations. plan as bonus, not baseline.
* also, your preface claims a “recent loss of x.com community notes and facebook fact checker.” treat this as **time-sensitive and verify before publishing**; otherwise credibility takes a hit. Rephrase: “with shifts in community notes/fact-checking availability…” and cite current status.&#x20;

## 2) precise text anchoring (selectors)

* quoting text on the web is fragile (DOM shifts, edits). specify a **selector strategy**:

  * **primary:** W3C Web Annotation **TextQuoteSelector** (exact/prefix/suffix text) + **TextPositionSelector** (start/end offsets).
  * **fallbacks:** CSS/XPath to nearest stable container; URL fragments; content hash of the nearest block.
  * **tolerance:** fuzz matching to survive minor edits; highlight drift if confidence < threshold.
* add a short algorithmic note: *resolve selectors → fetch page (or archive) → locate exact match → expand ±N sentences for context → render*.

## 3) link rot & page mutation

* quotes disappear or change. add durability:

  * **on create:** store a capture (link to Memento/Internet Archive, or your own lightweight snapshot).
  * **hashing:** store a **hash of the quoted string** and surrounding block; warn if current page no longer matches the hash.
  * **timestamp & version:** show capture time and “from archive vs live” badge.

## 4) author-chosen context ≠ objective context

* you note “the user decides relevant context.” that can be abused (cherry-picking). mitigate by:

  * a **toggle to expand automatic neutral context** (e.g., ±2 sentences / paragraph before & after), shown *in addition to* author-provided context.
  * a **disclosure chip**: “context provided by author • auto-context available.”
  * optionally, **community add-on context** (threaded, rate-limited), but that’s scope creep—plan later.

## 5) UI/UX specifics

* your ASCII mock is clear; specify component rules:

  * **quote block** (large typographic weight, copy icon, source URL, timestamp).
  * **context block** (collapsible; “N more sentences” affordance).
  * **drift badge** if source changed.
  * **truncation** rules (“… (open full quote)”) already mentioned—keep both quote and context truncation consistent.&#x20;
* placement logic for inline/ref cases is underdefined; give 2–3 deterministic rules and a fallback. you already flag a failing case; formalize it.&#x20;

## 6) security, privacy, abuse

* **PII leaks:** context expansion might surface unintended PII. add a **safety screen** (client-side regex/ML heuristic) before publishing.
* **copyright:** showing context may exceed fair use. defaults: short context, always link through, obey robots/copyright headers; publisher opt-out header (`meta name="contextgrabber" content="noembed"`).
* **phishing/spam:** signed share objects (see below) + rate limits.

## 7) trust & authenticity

* start simple: no grand reputation system. but define a **signed claim** format (JWS):

  * payload fields: `url`, `quote_text`, `context_bounds`, `selectors`, `created_at`, `source_hash`, `archive_url`, `display_opts`.
  * signature by creator (optional; keypair) or by your service for tamper-evidence.
* later, allow **org-verified keys** (newsrooms, journals) to sign shares.
