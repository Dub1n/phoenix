## Overview

This guide provides everything needed to create a backend service that integrates seamlessly with Templum's universal interface orchestrator. Templum 1.2's **zero backend knowledge architecture** means your backend can integrate with **zero modifications** to Templum code.

### What is Templum?

Templum is a universal interface orchestrator that provides consistent user experiences across multiple interface modalities:

- **VSCode Extension**: Rich IDE integration with tree views, panels, and commands
- **CLI Interface**: Interactive terminal-based menus and navigation
- **Command-Line**: Standard CLI with flag parsing and completion

### Why Integrate with Templum?

**For Users:**

- **Unified Experience**: Same backend functionality available in VSCode, CLI, and command-line
- **Interface Choice**: Use the interface that fits your workflow
- **Consistent Behavior**: Commands and data synchronize across all interfaces

**For Backend Developers:**

- **Zero UI Development**: Templum handles all interface rendering
- **Universal Access**: Single backend implementation supports all interface types
- **Automatic Discovery**: Templum finds and connects to your backend automatically
- **Protocol Flexibility**: Choose the communication protocol that fits your architecture

## Quick Start

## Capability Tiers

Templum discovers backend capabilities through the `backendConfig.capabilities` array (and mirrored manifest metadata). Each backend must supply the core capability set; optional capabilities can be advertised when available.

| Tier | Capability Flag | Description |
| --- | --- | --- |
| Core (required) | `command-routing` | Backend supplies a skin definition, accepts command execution requests, and exposes at least one discovery path (manifest drop, explicit config, or port scan). |
| Core (optional) | `discovery-manifest` | Drops enriched `.templum/services/*.json` files for zero-config discovery. |
| Core (optional) | `discovery-scan` | Listens on the standard discovery ports (3001–3004) with a recognisable probe endpoint. |
| Enhanced (optional) | `health` | Provides `GET /health` for runtime checks (used by Phase 6/health scripts when present). |
| Enhanced (optional) | `telemetry` | Emits structured performance metrics, enabling readiness/baseline diffs. |
| Enhanced (optional) | `ipc` / `websocket` | Offers alternative transports (Haruspex/PCL parity). |
| Enhanced (optional) | `streaming` | Streams command output (chunked HTTP responses or auxiliary channel) for long-running operations; adapters fall back to buffered output when absent. |
| Enhanced (optional) | `state` | Exposes a lightweight state snapshot endpoint or includes `state` blocks in command responses so multi-step workflows can reconcile progress. *(Post-MVP: capability reserved; runtime support pending.)* |

Backends can implement only the core tier for simple CLI wrappers (e.g., mapping `rg` invocations to a menu). When enhanced capabilities are present, advertise them via the `capabilities` array so Templum can automatically enable the corresponding features.

> **MVP note:** The canonical mock backend bundled with Templum enables `health`, `telemetry`, and `ipc` capabilities so existing validation suites (Phase 6, backend router, IPC harnesses) exercise the full transport/telemetry surface. `streaming` and `state` remain reserved for post-MVP follow-ups; backends may ignore those until their respective tasks land.

### 1. Minimal Backend Example

Here's a minimal HTTP-based backend that integrates with Templum:

**Backend Service (Python/Flask example):**

```python
from flask import Flask, jsonify, request

app = Flask(__name__)

# Skin definition - tells Templum how to integrate
SKIN_DEFINITION = {
    "id": "example-backend",
    "name": "Example Backend Service",
    "version": "1.0.0",
    "backendConfig": {
        "service": "example-backend",
        "protocol": "http",
        "endpoint": "http://localhost:5000",
        "authentication": {"type": "none"},
        "capabilities": ["command-routing"]
    },
    "commands": {
        "example.hello": {
            "id": "example.hello",
            "label": "Say Hello",
            "description": "Returns a hello message",
            "parameters": [
                {"name": "name", "type": "string", "description": "Name to greet"}
            ]
        }
    },
    "views": {
        "treeViews": [{
            "id": "exampleTree",
            "name": "Example Tree",
            "contextValue": "example"
        }]
    },
    "menus": {
        "main": {
            "title": "Example Backend",
            "items": [
                {"label": "Say Hello", "command": "example.hello"}
            ]
        }
    }
}

@app.route('/getSkinDefinition', methods=['GET'])
def get_skin_definition():
    return jsonify(SKIN_DEFINITION)

@app.route('/executeCommand', methods=['POST'])
def execute_command():
    data = request.json
    command = data.get('command')
    args = data.get('args', {})
    
    if command == 'example.hello':
        name = args.get('name', 'World')
        return jsonify({
            "success": True,
            "result": f"Hello, {name}!",
            "metadata": {"command": command}
        })
    
    return jsonify({
        "success": False,
        "error": {
            "message": f"Unknown command: {command}",
            "code": "UNKNOWN_COMMAND"
        }
    })

if __name__ == '__main__':
    app.run(host='localhost', port=5000)
```

### Handling Long-Running Commands and Error Paths

- If your backend advertises the `streaming` capability, support chunked HTTP responses (e.g., Flask `Response(stream_with_context(...))`) or an auxiliary channel (WebSocket, Server-Sent Events) so Templum can display incremental output. Backends that omit the capability can continue returning buffered results; adapters fall back automatically.
- Always return structured errors:
  ```json
  {
    "success": false,
    "error": {
      "message": "grep exited with code 2",
      "code": "COMMAND_FAILED",
      "details": {"exitCode": 2}
    }
  }
  ```
  This allows adapters to surface failures consistently across interfaces.
- Provide at least one negative-path command for testing (for example, accept a flag that forces an error) so integration suites can assert failure handling.
- Reuse a shared execution helper (spawn/HTTP/IPC) to manage timeouts, logging, and capability toggles uniformly when wiring CLI tools or richer partner services.
- If you manage backend-side state, advertise the `state` capability and expose either a `GET /state` helper or include a `state` payload in command responses so skins can show confirmation screens; otherwise Templum aggregates user selections on the client side.

**Enhanced Auto-Registration (recommended):**

Add this to your backend to enable automatic discovery on ANY port:

```python
import os
import json
import atexit

def auto_register_service(port):
    """Auto-register with Templum's enhanced discovery system"""
    try:
        # Create services directory
        services_dir = os.path.expanduser('~/.templum/services')
        os.makedirs(services_dir, exist_ok=True)
        
        # Create service file
        service_file = os.path.join(services_dir, f'example-backend-{os.getpid()}.json')
        service_info = {
            "id": "example-backend",
            "name": "Example Backend Service", 
            "version": "1.0.0",
            "pid": os.getpid(),
            "endpoint": f"http://localhost:{port}",
            "protocol": "http",
            "health": f"http://localhost:{port}/health",
            "capabilities": ["command-routing", "health"],
            "started": int(time.time() * 1000),
            "port": port
        }
        
        with open(service_file, 'w') as f:
            json.dump(service_info, f, indent=2)
        
        print(f"Auto-registered service: {service_file}")
        
        # Auto-cleanup on exit
        def cleanup():
            try:
                os.unlink(service_file)
                print("Removed service registration")
            except:
                pass
        atexit.register(cleanup)
        
        return service_file
    except Exception as e:
        print(f"Auto-registration failed: {e}")
        return None

if __name__ == '__main__':
    port = int(os.environ.get('PORT', 5000))  # Any port!
    
    # Auto-register for enhanced discovery
    auto_register_service(port)
    
    app.run(host='localhost', port=port)
```

## Architecture Overview

### Self-Describing Backend Architecture

Templum's integration works through **self-describing backends**:

1. **Backend provides skin definition** describing its capabilities and interface requirements
2. **Templum discovers backend** using enhanced multi-strategy discovery:
   - **Auto-Registration**: `~/.templum/services/*.json` (any port)
   - **Manual Registry**: `~/.templum/service-registry.json` (legacy)
   - **Configuration**: User-defined backend configs  
   - **Port Scanning**: Fallback for unconfigured backends
3. **Templum creates appropriate connection** based on backend's protocol specification
4. **Templum renders interfaces** automatically from skin definition
5. **Commands route dynamically** to your backend based on skin command mappings

```mermaid
graph LR
    Backend[Your Backend Service] --> SkinDef[Skin Definition]
    SkinDef --> Discovery[Service Discovery]
    Discovery --> Connection[Connection Factory]
    Connection --> CommandRouter[Dynamic Command Router]
    CommandRouter --> Interfaces[VSCode + CLI + Command]
    Interfaces --> Users[End Users]
```

### Communication Protocols Supported

Templum supports multiple communication protocols - choose what fits your architecture:

| Protocol | Use Case | Benefits | Implementation |
|----------|----------|----------|----------------|
| **HTTP** | REST APIs, web services | Standard, firewall-friendly, stateless | Flask, Express, FastAPI |
| **WebSocket** | Real-time updates, streaming | Bidirectional, low latency, persistent | Socket.io, ws library |
| **IPC** | Local services, high performance | Fast, secure, process communication | Named pipes, Unix sockets |
| **gRPC** | *[Future v1.3]* High-performance RPC | Type-safe, efficient, streaming | gRPC libraries |

## Skin Definition Reference

### Complete Skin Definition Structure

The skin definition is a JSON object that describes your backend's capabilities and interface requirements:

```typescript
interface UniversalSkinDefinition {
  // Core identification
  id: string;                          // Unique backend identifier
  name: string;                        // Human-readable name
  version: string;                     // Backend version
  description?: string;                // Description for users
  
  // Backend connection configuration
  backendConfig: BackendConfig;        // How Templum connects to your backend
  
  // Interface definitions (choose what you need)
  commands?: SkinCommands;             // Command definitions
  views?: SkinViews;                   // VSCode interface definitions
  menus?: SkinMenus;                   // CLI interface definitions
  
  // Theming and appearance
  themes: Record<string, ThemeDefinition>;
  components: Record<string, ComponentSkin>;
  
  // Metadata and capabilities
  metadata: SkinMetadata;
  features?: FeatureMatrix;
}
```

### BackendConfig Specification

This tells Templum how to connect to your backend:

```typescript
interface BackendConfig {
  // Basic identification
  service: string;                     // Service identifier
  version: string;                     // Protocol version
  
  // Connection specification
  protocol: 'http' | 'websocket' | 'ipc'; // gRPC deferred to v1.3
  endpoint: string;                    // Connection endpoint
  
  // Authentication (optional)
  authentication?: {
    type: 'none' | 'basic' | 'bearer' | 'api-key' | 'oauth';
    credentials?: Record<string, string>;
    required?: boolean;
  };
  
  // Connection behavior
  timeout?: number;                    // Connection timeout (ms)
  retries?: number;                    // Retry attempts
  keepAlive?: boolean;                 // Keep connection alive
  
  // Service discovery endpoints
  healthEndpoint?: string;             // Health check endpoint
  capabilitiesEndpoint?: string;       // Capabilities endpoint
  
  // Protocol-specific options
  options?: { [key: string]: any };    // Protocol-specific settings
}
```

### Command Definitions

Commands define the actions your backend can perform:

```typescript
interface SkinCommands {
  [commandId: string]: {
    id: string;                        // Command identifier
    label: string;                     // Display name
    description?: string;              // Help text
    category?: string;                 // Command category
    parameters?: CommandParameter[];   // Input parameters
    returns?: string;                  // Return type description
    examples?: CommandExample[];       // Usage examples
  };
}

interface CommandParameter {
  name: string;                        // Parameter name
  type: 'string' | 'number' | 'boolean' | 'array' | 'object';
  description?: string;                // Parameter description
  required?: boolean;                  // Is required?
  default?: any;                       // Default value
  choices?: string[];                  // Valid choices
}
```

**Command Naming Convention:** Use dot notation with your backend prefix:

- ✅ Good: `mybackend.action`, `myservice.process`, `tool.analyze`
- ❌ Avoid: Generic names that might conflict with other backends

## Protocol Implementation Guides

### HTTP/REST Protocol

HTTP is the most common protocol for backend services. Templum expects specific endpoints:

**Required Endpoints:**

```http
GET /getSkinDefinition
POST /executeCommand
GET /health (optional)
GET /getCapabilities (optional)
```

**Complete HTTP Backend Example (Node.js/Express):**

```javascript
const express = require('express');
const app = express();
app.use(express.json());

// Skin definition
const skinDefinition = {
  id: 'nodejs-backend',
  name: 'Node.js Backend Service',
  version: '1.0.0',
  backendConfig: {
    service: 'nodejs-backend',
    protocol: 'http',
    endpoint: 'http://localhost:3000',
    authentication: { type: 'none' },
    healthEndpoint: '/health'
  },
  commands: {
    'nodejs.status': {
      id: 'nodejs.status',
      label: 'Get Status',
      description: 'Returns backend status information'
    },
    'nodejs.process': {
      id: 'nodejs.process',
      label: 'Process Data',
      description: 'Process data with options',
      parameters: [
        { name: 'data', type: 'string', required: true },
        { name: 'format', type: 'string', choices: ['json', 'xml', 'csv'] }
      ]
    }
  },
  views: {
    treeViews: [{
      id: 'nodejsTree',
      name: 'Node.js Services',
      contextValue: 'nodejs'
    }]
  },
  menus: {
    main: {
      title: 'Node.js Backend',
      items: [
        { label: 'Get Status', command: 'nodejs.status' },
        { label: 'Process Data', command: 'nodejs.process' }
      ]
    }
  },
  themes: {
    default: {
      name: 'Default',
      type: 'light',
      colors: {
        primary: { 500: '#007ACC' },
        secondary: { 500: '#6CB33E' }
      }
    }
  }
};

// Required: Skin definition endpoint
app.get('/getSkinDefinition', (req, res) => {
  res.json(skinDefinition);
});

// Required: Command execution endpoint
app.post('/executeCommand', (req, res) => {
  const { command, args = {} } = req.body;
  
  switch (command) {
    case 'nodejs.status':
      res.json({
        success: true,
        result: {
          status: 'healthy',
          uptime: process.uptime(),
          version: process.version,
          memory: process.memoryUsage()
        }
      });
      break;
      
    case 'nodejs.process':
      const { data, format = 'json' } = args;
      if (!data) {
        return res.json({
          success: false,
          error: 'Data parameter is required'
        });
      }
      
      // Process data based on format
      let result;
      switch (format) {
        case 'json':
          result = JSON.stringify({ processed: data });
          break;
        case 'xml':
          result = `<result><data>${data}</data></result>`;
          break;
        case 'csv':
          result = `data\n"${data}"`;
          break;
        default:
          return res.json({
            success: false,
            error: `Unknown format: ${format}`
          });
      }
      
      res.json({
        success: true,
        result: { processed: result, format }
      });
      break;
      
    default:
      res.json({
        success: false,
        error: `Unknown command: ${command}`
      });
  }
});

// Optional: Health check endpoint
app.get('/health', (req, res) => {
  res.json({
    status: 'healthy',
    timestamp: new Date().toISOString(),
    uptime: process.uptime()
  });
});

// Optional: Capabilities endpoint
app.get('/getCapabilities', (req, res) => {
  res.json({
    commands: Object.keys(skinDefinition.commands),
    protocols: ['http'],
    version: skinDefinition.version
  });
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`Backend service running on port ${PORT}`);
  console.log(`Skin definition: http://localhost:${PORT}/getSkinDefinition`);
});
```

**HTTP Protocol Features:**

- ✅ Stateless and scalable
- ✅ Standard REST patterns
- ✅ Easy debugging with curl/Postman
- ✅ Firewall and proxy friendly
- ✅ Built-in authentication support

### WebSocket Protocol

WebSocket enables real-time bidirectional communication:

**WebSocket Backend Example (Node.js/ws):**

```javascript
const WebSocket = require('ws');
const http = require('http');

// Create HTTP server for initial handshake
const server = http.createServer();
const wss = new WebSocket.Server({ server });

const skinDefinition = {
  id: 'websocket-backend',
  name: 'WebSocket Backend Service',
  version: '1.0.0',
  backendConfig: {
    service: 'websocket-backend',
    protocol: 'websocket',
    endpoint: 'ws://localhost:8080',
    authentication: { type: 'none' }
  },
  commands: {
    'ws.subscribe': {
      id: 'ws.subscribe',
      label: 'Subscribe to Updates',
      description: 'Subscribe to real-time updates',
      parameters: [
        { name: 'channel', type: 'string', required: true }
      ]
    },
    'ws.send': {
      id: 'ws.send',
      label: 'Send Message',
      description: 'Send a message to all subscribers',
      parameters: [
        { name: 'channel', type: 'string', required: true },
        { name: 'message', type: 'string', required: true }
      ]
    }
  }
};

// Store active subscriptions
const subscriptions = new Map();

wss.on('connection', (ws) => {
  console.log('New client connected');
  
  ws.on('message', (data) => {
    try {
      const message = JSON.parse(data);
      
      switch (message.type) {
        case 'getSkinDefinition':
          ws.send(JSON.stringify({
            id: message.id,
            type: 'skin_definition_response',
            success: true,
            data: skinDefinition
          }));
          break;
          
        case 'executeCommand':
          handleCommand(ws, message);
          break;
          
        default:
          ws.send(JSON.stringify({
            id: message.id,
            type: 'error',
            success: false,
            error: `Unknown message type: ${message.type}`
          }));
      }
    } catch (error) {
      ws.send(JSON.stringify({
        type: 'error',
        success: false,
        error: error.message
      }));
    }
  });
  
  ws.on('close', () => {
    // Clean up subscriptions
    for (const [channel, subscribers] of subscriptions.entries()) {
      subscribers.delete(ws);
      if (subscribers.size === 0) {
        subscriptions.delete(channel);
      }
    }
    console.log('Client disconnected');
  });
});

function handleCommand(ws, message) {
  const { command, args = {} } = message.payload;
  
  switch (command) {
    case 'ws.subscribe':
      const { channel } = args;
      if (!subscriptions.has(channel)) {
        subscriptions.set(channel, new Set());
      }
      subscriptions.get(channel).add(ws);
      
      ws.send(JSON.stringify({
        id: message.id,
        type: 'command_response',
        success: true,
        result: `Subscribed to channel: ${channel}`
      }));
      break;
      
    case 'ws.send':
      const { channel: sendChannel, message: userMessage } = args;
      const subscribers = subscriptions.get(sendChannel);
      
      if (subscribers) {
        subscribers.forEach(client => {
          if (client.readyState === WebSocket.OPEN) {
            client.send(JSON.stringify({
              type: 'notification',
              channel: sendChannel,
              message: userMessage,
              timestamp: new Date().toISOString()
            }));
          }
        });
      }
      
      ws.send(JSON.stringify({
        id: message.id,
        type: 'command_response',
        success: true,
        result: `Message sent to ${subscribers ? subscribers.size : 0} subscribers`
      }));
      break;
      
    default:
      ws.send(JSON.stringify({
        id: message.id,
        type: 'command_response',
        success: false,
        error: `Unknown command: ${command}`
      }));
  }
}

server.listen(8080, () => {
  console.log('WebSocket backend listening on port 8080');
});
```

- ✅ Real-time bidirectional communication
- ✅ Low latency for live updates
- ✅ Persistent connections
- ✅ Event streaming capabilities
- ✅ Efficient for high-frequency updates

### IPC Protocol

IPC (Inter-Process Communication) provides high-performance local communication:

**IPC Backend Example (Node.js):**

```javascript
const net = require('net');
const fs = require('fs');
const path = require('path');

const skinDefinition = {
  id: 'ipc-backend',
  name: 'IPC Backend Service',
  version: '1.0.0',
  backendConfig: {
    service: 'ipc-backend',
    protocol: 'ipc',
    endpoint: '/tmp/ipc-backend.sock', // Unix socket
    // On Windows: '\\\\.\\pipe\\ipc-backend'
    authentication: { type: 'none' },
    options: {
      workspaceMarkers: ['.git', 'package.json'],
      connectionDir: '.templum',
      connectionFile: 'ipc-backend-connection.json'
    }
  },
  commands: {
    'ipc.analyze': {
      id: 'ipc.analyze',
      label: 'Analyze File',
      description: 'Perform file analysis',
      parameters: [
        { name: 'filepath', type: 'string', required: true },
        { name: 'deep', type: 'boolean', default: false }
      ]
    }
  }
};

// Create IPC server
const server = net.createServer((socket) => {
  console.log('Client connected via IPC');
  
  socket.on('data', (data) => {
    try {
      const message = JSON.parse(data.toString());
      
      switch (message.type) {
        case 'getSkinDefinition':
          socket.write(JSON.stringify({
            id: message.id,
            type: 'skin_definition_response',
            success: true,
            data: skinDefinition
          }) + '\n');
          break;
          
        case 'executeCommand':
          handleIPCCommand(socket, message);
          break;
          
        default:
          socket.write(JSON.stringify({
            id: message.id,
            type: 'error',
            success: false,
            error: `Unknown message type: ${message.type}`
          }) + '\n');
      }
    } catch (error) {
      socket.write(JSON.stringify({
        type: 'error',
        success: false,
        error: error.message
      }) + '\n');
    }
  });
  
  socket.on('end', () => {
    console.log('Client disconnected from IPC');
  });
});

function handleIPCCommand(socket, message) {
  const { command, args = {} } = message.payload;
  
  switch (command) {
    case 'ipc.analyze':
      const { filepath, deep = false } = args;
      
      try {
        const stats = fs.statSync(filepath);
        const result = {
          filepath,
          size: stats.size,
          modified: stats.mtime.toISOString(),
          type: path.extname(filepath),
          deep: deep ? 'performed' : 'skipped'
        };
        
        socket.write(JSON.stringify({
          id: message.id,
          type: 'command_response',
          success: true,
          result
        }) + '\n');
      } catch (error) {
        socket.write(JSON.stringify({
          id: message.id,
          type: 'command_response',
          success: false,
          error: `File analysis failed: ${error.message}`
        }) + '\n');
      }
      break;
      
    default:
      socket.write(JSON.stringify({
        id: message.id,
        type: 'command_response',
        success: false,
        error: `Unknown command: ${command}`
      }));
  }
}

// Start IPC server
const socketPath = skinDefinition.backendConfig.endpoint;

// Clean up existing socket
if (fs.existsSync(socketPath)) {
  fs.unlinkSync(socketPath);
}

server.listen(socketPath, () => {
  console.log(`IPC backend listening on ${socketPath}`);
  
  // Create connection info file for discovery
  const connectionInfo = {
    service: skinDefinition.id,
    protocol: 'ipc',
    endpoint: socketPath,
    pid: process.pid,
    startTime: new Date().toISOString()
  };
  
  const connectionDir = '.templum';
  const connectionFile = path.join(connectionDir, 'ipc-backend-connection.json');
  
  if (!fs.existsSync(connectionDir)) {
    fs.mkdirSync(connectionDir, { recursive: true });
  }
  
  fs.writeFileSync(connectionFile, JSON.stringify(connectionInfo, null, 2));
});

// Cleanup on exit
process.on('SIGINT', () => {
  if (fs.existsSync(socketPath)) {
    fs.unlinkSync(socketPath);
  }
  process.exit();
});
```

- ✅ Highest performance for local communication
- ✅ Secure (no network exposure)
- ✅ Low latency and high throughput
- ✅ Operating system native
- ✅ Perfect for development tools

2. **Registry Discovery** - service registry entries
3. **Endpoint Scanning** (lowest priority) - automatic port scanning

## Manual Overrides & Watchers

When a real backend needs to be force-promoted (for example, during partner validation), operators can drop a sanitized manifest into `.templum/services/<serviceId>.json`. The file watcher feeds the same parsing path used during automated discovery, ensuring manual overrides stay zero-knowledge:

1. Create the `.templum/services/` directory in the workspace if it does not exist.
2. Write a manifest that matches the `serviceManifestSchema` (see `src/backend/schemas/service-manifest.ts`). At minimum include `id`, `endpoint`, `protocol`, and an optional `healthCheck` block.
3. Templum emits `serviceDiscovered` once the file is seen; call `TemplumCore.applyManualOverride(serviceId)` (or trigger the CLI command `templum.manualOverride.apply`) to promote the backend. The CLI/VSC commands hash the identifiers before logging so secrets never leak.
4. Removing the manifest file automatically clears the override (`manualOverride:cleared` event) and reverts to discovery-driven routing.

The watcher flow is covered by `src/tests/backend/manual-override-watcher.integration.test.ts`, which drops manifests, asserts overrides emit sanitized descriptors, and verifies the system auto-cleans when the manifest disappears. Keep the test green whenever altering discovery or override logic.

#### Phase 6 Integration Validation Harness

Templum ships a Phase 6 validation harness that now defaults to mock backends while enforcing the real API contracts. Use it to catch payload drift before touching live services:


   Useful for pipeline jobs that already verified mock contracts and only need the live check.

```typescript
  type: 'skin_definition_response' | 'command_response' | 'pong' | 'error';
  success: boolean;
  data?: any;               // Response data
  error?: string;           // Error message
  timestamp: number;        // Unix timestamp
}
```

```typescript
  timestamp: number;        // Unix timestamp
}
```

Messages are terminated with a newline character (`\n`).
