# Templum CLI Character-Grid Decision Record

**Bottom Line**
Yes, a full character-grid rewrite makes sense, and I think it is the cleanest way to recover the CLI.

The important refinement is: pages should not manually assign every character coordinate. Build a declarative page/window tree, calculate rectangles, then rasterise those components into a 2D terminal-cell buffer.

```text
Skin + service state + session state
                ↓
           CLI view model
                ↓
        measure and layout
                ↓
     page/window component tree
                ↓
      terminal cell buffer [x,y]
                ↓
        ANSI terminal painter
```

A cell should contain a grapheme and style separately, rather than storing ANSI-decorated strings:

```ts
interface Cell {
  text: string;
  foreground?: Color;
  background?: Color;
  attributes?: CellAttributes;
}
```

This is effectively a small terminal framebuffer.

**Current State**
Your diagnosis is directionally correct: backend discovery, skin loading, session state, and command execution are not the main reason the CLI looks and behaves incorrectly. However, the data is not consistently reaching the live interactive presentation.

The current runtime has competing paths:

- `applySkin()` sends the skin through `EnhancedWindowSystem`, `UniversalLayoutEngine`, and `ContentLayoutSystem`.
- That procedural path can produce bordered strings, but it generates every reachable window and may print several windows rather than maintaining one active page.
- The actual interactive loop calls `InteractiveMenuRenderer.displayMenu()`.
- `displayMenu()` uses Inquirer and menus created by `initializeDefaultMenus()`.
- Those menus are hardcoded and independent of the procedural windows just printed.
- A more window-oriented `displayEnhancedMenu()` exists, but the live loop does not call it.
- Commands, status displays, errors, spinners, prompts, and recommendations can still write directly to stdout outside either renderer.

So the current flow is effectively:

```text
Skin → procedural window strings → stdout

Hardcoded menu state → Inquirer → separate interactive UI

Commands/status/errors → assorted direct stdout writes
```

There is no single owner of the terminal surface.

That explains most of `CLI-remaining-issues.md`: fixing a local formatting method cannot fix focus, input placement, confirmations, timeouts, window stacking, or output appearing outside the window.

**How CLI 2.1 Differs**
`CLI-design-2.1-architecture-data-flow.md` proposes useful concepts:

- Window Manager
- content-based measurement
- bordered windows
- page/content separation
- in-window text input
- skin-driven routing
- unified navigation

But it still largely describes components generating strings and sending a `windowString` to a console renderer. It does not define a complete terminal surface, cell composition, clipping, overlapping-window composition, or a single input/render loop.

The character-grid design would be a stronger implementation of CLI 2.1, not a rejection of it:

| Current implementation                    | Documented CLI 2.1          | Character-grid rewrite              |
| ----------------------------------------- | --------------------------- | ----------------------------------- |
| Several string renderers                  | Coordinated window renderer | One terminal framebuffer            |
| Inquirer owns interaction                 | Enhanced input component    | One event loop and state reducer    |
| Direct stdout throughout                  | Console renderer            | Only terminal backend writes stdout |
| Layout rules duplicated                   | Window/page calculators     | Measure/arrange once                |
| ANSI mixed into strings                   | Theme-aware strings         | Style stored per cell               |
| Procedural and interactive views separate | Intended coordination       | Same scene drives display and input |

**Recommended Architecture**
I would introduce a dedicated CLI renderer rather than extending `UniversalLayoutEngine` further:

```text
CliApplication
  ├── CliStateReducer
  ├── CliViewModelBuilder
  ├── CliLayoutEngine
  ├── CliSceneComposer
  ├── CellBuffer
  ├── TerminalPainter
  └── TerminalInputController
```

The scene composer should use primitives such as:

```ts
canvas.fill(rect, style);
canvas.drawBorder(rect, borderStyle);
canvas.writeText(point, title, style);
canvas.drawMenu(rect, items, selectedIndex);
canvas.drawTextBox(rect, inputState);
canvas.blit(childCanvas, origin);
```

Each component receives local bounds. It should not know its absolute terminal coordinates.

This design would naturally support:

- nested and overlapping windows
- exact three-cell page padding
- centred titles
- selector movement across the separator
- disabled Back/Home items
- in-window command input
- exit and Ctrl+C confirmation as state changes
- resizing and clipping
- full-frame snapshot tests
- optional frame-diff painting later

Wide characters and combining characters need explicit handling because terminal cells are not quite pixels. `string-width` and `Intl.Segmenter` can cover that without bringing ANSI escapes into measurement.

**What I Would Preserve**
I would retain the orchestrator, service discovery, validated skin payloads, command routing, service ordering, and session bridge.

I would replace or retire the CLI responsibilities currently spread across:

- `interactive-menu-renderer.ts`
- `terminal-ui-components.ts`
- `enhanced-window-system.ts`
- `content-layout-system.ts`
- the CLI branch of `universal-layout-engine.ts`
- much of `cli-display-consistency-engine.ts`
- direct presentation logic in `cli-adapter-abstracted.ts`

`cli-generator.ts` may remain useful, but it should produce a neutral CLI view model, not rendered strings or a second navigation system.

**Assessment**
The renderer is not absent; it is overimplemented and underintegrated. Several partial systems each solve part of the problem, while none controls the complete interactive frame.

A clean CLI-specific rewrite is justified. Rewriting backend or skin transport would be unnecessary scope. The boundary should be:

```text
Preserve validated domain data and actions
Replace everything from CLI view-model construction through terminal input/output
```

The existing tests are not strong enough to prevent visual regressions. The focused suites pass, but they mostly assert that expected words and border characters occur. A passing captured window is visibly misaligned and violates several 2.1 rules. Golden full-frame tests based on `2.1_examples.ASCII`, plus keyboard-event workflow tests, should define the replacement.

Validation performed: `npm run build` passed; the focused renderer and adapter suites passed all 47 tests with coverage disabled. No files were changed.
